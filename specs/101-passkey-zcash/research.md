# Research: Passkey-native Zcash (spec 101)

Phase 0 output. Each entry: Decision / Rationale / Alternatives considered.
Spec 063's research §D (Zcash, transparent-only) already settled several of
these questions for the *legacy-recovery* path; this feature adopts those
findings where they transfer and records here what is different for the
passkey-native wallet. All Technical Context unknowns from plan.md resolve
here.

## R1. Key material: derive from the spec-041 master seed

**Decision**: The Zcash wallet root derives client-side from the existing
per-account master seed, exactly as Bitcoin does (spec 061 R1), under a new
domain-separated HKDF info string:

```
masterSeed (32B, spec 041, PRF-recoverable)
  → HKDF-SHA256(salt = 32 zero bytes, info = "fairwins-zec-seed-v1", L = 64)
  → BIP32 root (@scure/bip32)
  → account m/44'/{coin}'/0'   (coin = 133' mainnet, 1' testnet)
  → receive m/44'/{coin}'/0'/0/i  (P2PKH t-addresses)
```

Full normative detail in [contracts/key-derivation-zec.md](./contracts/key-derivation-zec.md).

**Rationale**: FR-001/FR-003 demand a deterministic, recoverable wallet with no
new backup artifact; the master seed is the platform's one root with exactly
those properties, and the info-string domain separation guarantees the ZEC tree
can never collide with the KEK path, the BTC tree, or future consumers.
Availability follows the seed (PRF passkey accounts only) and is disclosed
honestly — same matrix as Bitcoin.

**Alternatives**: new BIP-39 mnemonic (violates no-new-backup-artifact); reuse
of the BTC HKDF output with a different path (rejected — cross-chain trees must
be unlinkable at the seed level, and an info string is the established
mechanism); deriving from the passkey P-256 key directly (impossible —
non-deterministic signatures, unextractable key; spec 041 settled this).

**Coin-type note**: mainnet uses SLIP-44 133'. For `'zcash-testnet'` this
contract picks **1'** (the SLIP-44 shared-testnet convention, mirroring the
BTC contract's 0'/1' pair). Spec 063's research observed real wallets diverge
on testnet (1 vs 133) — that matters for *recovering foreign seeds* (063 scans
both); for our own canonical wallet we simply pick one and pin it.

## R2. Transaction construction & signing: hand-rolled v5 + ZIP-244, vector-gated

**Decision**: Build a small, quarantined signing module in
`frontend/src/lib/zcash/` — v5 (NU5+) transaction serializer + ZIP-244
signature digest — on the audited primitives already shipped:
`@noble/hashes/blake2b` (supports the required 16-byte personalization and
`dkLen: 32`), `@noble/curves/secp256k1` (ECDSA), `@scure/bip32`, `@scure/base`
(base58check). **No new runtime dependency.**

**Rationale** (adopts 063 research §D): `@scure/btc-signer` does **not**
support Zcash (no `nVersionGroupId`/`nConsensusBranchId`/BLAKE2b sighash), so
there is no off-the-shelf path in our stack. Transparent-only collapses the
ZIP-244 digest tree — the Sapling/Orchard bundle digests are fixed
empty-bundle constants — leaving `header_digest` + `transparent_digest` (+ the
per-input amounts/scripts digests) as the implementation surface. That is
tractable, and the risk is concentrated in exactly one module.

**The gate is the design**: the sighash is consensus-critical and a wrong
digest signs a transaction the network rejects (funds stuck in a bad flow) or
— worse with a subtly wrong input commitment — signs something other than what
the member confirmed. Therefore (SC-004, CI-blocking before any mainnet path):

1. the official `zcash/zips` ZIP-244 reference vectors (generated by the ZIP's
   `zip244.py` reference implementation) are committed as fixtures and must
   pass; and
2. a **differential oracle** — `@bitgo/utxo-lib`, added as a *test-only* dev
   dependency (never shipped in the bundle) — must produce byte-identical
   digests over a generated corpus of transparent v5 transactions.

**Alternatives**: `@bitgo/utxo-lib` as the shipping signer (rejected — heavy,
foreign to the `@scure`/`@noble` stack, and its bundle cost lands on every
member; kept as the oracle instead); WASM librustzcash bindings (rejected —
new toolchain and megabytes of WASM for a transparent-only wallet);
pre-v5/ZIP-243 support (rejected — v1 signs v5 only; every post-NU5 node
accepts v5).

**Lockfile note**: adding the test-only oracle touches the root lockfile —
follow the `monorepo-workspace` skill (`npm run deps:reinstall`, exact pin,
`check:deps` green); npm/cli#4828 is a real hazard here (spec 075).

## R3. Gateway upstream: Blockbook REST, proxied; lightwalletd rejected for v1

**Decision**: The optional gateway module `services/relay-gateway/src/zcash/`
(`ZEC_*` env) proxies a **Blockbook** instance (Trezor's indexer; public
instances exist for Zcash, and `ZEC_BLOCKBOOK_URL` is config-swappable to a
self-hosted one). Blockbook's REST API provides everything the transparent
wallet needs in the same fetch/normalize/cache shape as the Bitcoin module's
Esplora upstream: address balances + history (`/api/v2/address/{taddr}`),
UTXOs (`/api/v2/utxo/{taddr}`), transaction detail (with the vjoinsplit/
valueBalance/shielded-spend fields the shielded-involvement flag needs),
broadcast (`/api/v2/sendtx/`), and chain tip height (`/api/v2/`).

**Rationale**: the relay-gateway's module pattern (polymarket → bitcoin →
perps) is plain HTTPS fetch + TTL cache + quotas + killswitch; Blockbook drops
straight into it with zero new dependencies. **lightwalletd was considered and
rejected for v1**: it speaks gRPC (the gateway would need a gRPC client dep or
a gRPC-web bridge — a lockfile and infra cost), it is optimized for shielded
compact-block scanning we cannot use, and its transparent-address APIs
(`GetTaddressTxids`, `GetTaddressBalance`) are a subset of what Blockbook
already exposes over REST. This mirrors 063 research §D's conclusion
("Blockbook REST proxied through the relay-gateway; lightwalletd optional").
A zebrad/zcashd JSON-RPC node is the *optional* branch-id source (R4), not the
data plane.

**Alternatives**: lightwalletd (rejected above); zcashd/zebrad JSON-RPC as the
whole data plane (rejected — no indexed address→UTXO lookup without
`insightexplorer`-style indexes and node ops burden); client-direct explorer
calls (rejected — leaks the member's address set to a third party with no
quota/killswitch/cache layer; same reasoning as Bitcoin R4).

## R4. Consensus branch id: live, layered, fail-closed

**Decision**: `GET /v1/zcash/:network/consensus` returns
`{ height, consensusBranchId }`. The gateway resolves the branch id by:

1. **Primary**: a maintained network-upgrade activation table (upgrade name,
   activation height, branch id — public consensus constants) evaluated
   against the **live tip height** from Blockbook. The table is data, but the
   *selection* is live: a stale deployment cannot sign across an upgrade
   boundary because…
2. **Fail-closed rule**: if the live tip height is at or beyond the first
   activation height the table does not know (i.e. a network upgrade the
   deployment predates), the endpoint reports the branch id as
   `unconfirmed` — and the client refuses to sign (FR-019), while balances
   and receiving keep working.
3. **Optional override**: `ZEC_NODE_RPC_URL` (a zebrad/zcashd JSON-RPC
   endpoint) lets ops source `{height, branchId}` from `getblockchaininfo`
   directly, which self-updates across upgrades.

**Rationale**: 063 research is blunt — "`nConsensusBranchId` MUST be fetched
live … a hardcoded branch id breaks at the next network upgrade." A bare
constant in the client is the failure mode; a table + live-height selection +
fail-closed past the table's knowledge gives the correct behavior in every
state: current deployments sign correctly, stale deployments *stop signing*
with an honest reason instead of producing consensus-invalid signatures, and
funds are never at risk (a wrong branch id yields an invalid signature, but
"invalid" is a stranded member and a broken promise — blocked-with-reason is
the honest version).

## R5. Fees: ZIP-317 conventional fee, member-confirmed hard ceiling

**Decision**: Compute the ZIP-317 conventional fee client-side from the
transaction's shape: `fee = marginal_fee(5000 zats) × max(grace(2),
logical_actions)`, where for a transparent-only transaction
`logical_actions = max(nIn, nOut)`. The confirm UI shows it in ZEC + USD; the
member-confirmed fee is a **hard signing ceiling** (refuse-to-sign on
overrun), and the quote carries 60s freshness so a changed input set forces
re-confirmation — behavioral parity with Bitcoin's `FeeOverrunError` rule even
though the ZIP-317 formula is deterministic (the ceiling guards against
*implementation* drift between quote and build, not market drift).

**Rationale**: ZIP-317 is what current node relay policy expects; paying it
exactly avoids both stuck transactions (underpay) and waste (overpay). There
is no fee market to estimate in normal conditions — simpler and *more* honest
than Bitcoin's rate estimation. Dust: change below 546 zats folds into the
fee (conservative Bitcoin-inherited threshold; Zcash standardness derives from
the same upstream rules), disclosed in the fee line.

## R6. Shielded involvement detection (unsupported-holdings)

**Decision**: The gateway normalizer marks every transaction DTO with
`involvesShieldedPool: boolean` — true when the raw tx carries Sapling
spends/outputs, Orchard actions, a nonzero `valueBalance`, or legacy
JoinSplits (all visible in Blockbook's tx detail). The client ORs this over
wallet history into the wallet-level `unsupported-holdings` disclosure state
(spec FR-011..013). When the upstream cannot report shielded components
(missing fields), the DTO is marked `shieldedVisibility: 'unknown'` and the
client discloses that completeness could not be checked — degraded detection
never silently asserts a complete balance.

**Rationale**: the client cannot see shielded balances *by construction*
(that's the point of shielding); the only honest rendering is "transparent
balance + here is why it may not be everything". Rendering an empty/zero
balance to a member whose funds sit in Orchard would be constitution-III
fabrication.

## R7. Rotation & discovery: mirror Bitcoin exactly

**Decision**: Rotate receive addresses per request; gap-limit-20 discovery on
the external chain; never-decreasing cursor; recovery = rescan-and-max. No
Zcash-specific deviation.

**Rationale**: transparent Zcash inherits Bitcoin's address-reuse privacy
weakness unchanged, and the BIP-44 external-chain layout makes the Bitcoin
discovery convention directly applicable. If anything, rotation matters more
here: members may wrongly assume "Zcash" implies privacy, so the transparent
wallet should at least not add reuse linkage on top. One chain (external) per
account keeps discovery identical to the BTC contract (change returns to the
next unissued external address; change chain reserved).

## R8. Network registry: parallel string ids (established pattern)

**Decision**: `frontend/src/config/zcashNetworks.js` with string ids
`'zcash'` / `'zcash-testnet'`, `isZcashNetworkId` boundary guard, per-network
address prefixes, explorer links, capability set, testnet/mainnet pairing —
the third instance of the pattern `bitcoinNetworks.js` established and
`solanaNetworks.js` repeated. Never a numeric chainId; ids never reach
`getContractAddressForChain`/wagmi/subgraph code. This is the same file spec
063's task list names (its T003) — 101 creates it; 063-US4 reuses it as-is.
